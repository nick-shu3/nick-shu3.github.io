# スロ探究の共通テンプレート

公開HTMLは `pages/*.json` と共通レイアウト `build.py`、共通CSSから生成します。
JSONのbodyは編集者が確認した静的本文です。ブラウザーで入力や外部データをHTMLとして取り込む機能はありません。
既存CSP・スタンドアロンガード・CIを維持し、生成したすべての公開ページを既存検査の対象にします。

## 記事の役割と共通構成

| 種類 | 場所 | 本文の順序 |
|---|---|---|
| 機種ガイド | machines/機種/ | 掲載範囲→重要度一覧→条件・評価理由・記録方法→設定別データ→関連実戦→出典・履歴 |
| 機種別実戦 | records/日付/機種/ | 結果・発見→主要場面→判断・所感→全データ→未確認事項・確認元→関連ガイド |
| 当日まとめ | records/日付/ | 当日の収支→実戦の順序→各機種の記事へのリンク |
| トップ | サイト直下 | サイトで分かること→目的別の入口→実戦・機種ガイド・日程・ニュース |
| 777リーグ | league/777league/ | 本編公開開始・決起集会の公開予定→月別の収録日・終了状況・放送日→確認元 |
| 新台カレンダー | new-machines/ | 情報基準日・予定の扱い→月別カレンダー→機種・導入予定・確認元 |
| 業界ニュース | news/ | 号の日付→事実要約→読者に関わる考察→確認元・未確認事項 |
| スロ番組ウォッチ | watch/、watch/記事ID/ | 公式動画リンク→ネタバレなしの概要→本人コメント（任意）→紹介元・関連記事 |

機種ガイドに日付ごとの実戦全文を蓄積しません。機種別記事に他機種の数値や合計収支を混ぜません。
当日まとめでのみ、当日の複数機種の収支を合算します。機種別と日付別を相互リンクします。

## 新しい記事を追加する手順

1. `templates/` の該当JSONを `pages/` にコピーし、固有名で保存。
2. path、title、description、short_title、updated、status、breadcrumbs、toc、bodyを編集。
3. 機種別実戦では、総Gと通常G、ボーナス内訳、投資・回収・差枚の集計単位を確認。未記録は空欄を埋めず「未確認」と記載。
4. タイトルは実測した疑問・展開を具体的に。設定・勝率・内部抽選は未確認のまま断定しない。
5. 機種ガイドの関連実戦、日付まとめ、実戦一覧、トップの最新記事を更新。
6. `python3 scripts/slot-tankyu/build.py` でHTMLを生成し、`python3 scripts/slot-tankyu/check.py` でリンク・アンカー・メタ情報・共有画像・生成結果の一致を確認。
7. PNG共有画像は1200×630。必要ならPillowと日本語フォントを用意して `python3 scripts/slot-tankyu/share_images.py --font /path/to/font.otf` で再生成。フォントは公開HTMLに配信しない。見出しの単語が途中で切れる場合は、ページJSONの `share_lines` に最大4行の文字列配列を指定する。各行は共有画像の横幅内に収める。
8. 下記検査と表示確認後、ユーザー承認を得てPRを作り、最新HEADのverify成功後に公開。

## 表記ルール

- S/A/B/C＝編集上の重要度。数値の確度・設定期待度・勝率とは別。
- 根拠＝公式情報／解析情報／実戦／未確認。根拠区分にA/Bを使わない。
- ヘッダーは記事の種類や実戦日を示す。「公開中・確認継続中」など制作側の進捗表示は載せない。
- 一覧は重要度・項目・詳細リンクのみ。評価理由と記録方法は詳細に記載。
- 長い数表・確認メモは詳細欄へ。本文には主要場面と読者に役立つ発見を残す。
- 訂正時は現在の確定記録を優先し、途中報告は履歴だと明記。
- 編集方針は共通ページに集約。各記事にはその項目固有の制約を記載。

## 検査

Gitleaks redacted、`node tests/security.cjs`、`node tests/security-regression.cjs`、`node tests/release.cjs`、リンク・アンカー・メタ情報・共有画像、生成の再現性、スマホ/PC表示、直接表示/iframe内非表示を確認。
未実施は合格扱いにしない。canonicalは既存資材チェックと整合する同一ページ相対URL、og:urlは公開先の絶対URL。
SNS各社でのカード表示は別途確認する。OGPが存在するだけではSNS上の描画成功や拡散を保証しない。

公開運用は週約1時間を目安に、一つの実戦メモから記事・ガイド更新へ展開します。

## Search Consoleの所有権確認

トップのpages/home.jsonにgoogle_site_verificationを保持し、生成時にトップのheadへ公開用確認メタタグを出力します。Googleにログインする認証情報ではありません。記事の更新時にもこの設定を維持してください。外部スクリプト・計測通信・CSP変更は追加していません。Search Consoleで確認できるのはGoogle検索の表示/クリック等であり、サイト全体のPV計測とは別です。

## 読者向けの文章と写真

- 本文は「何が起きたか」「何が分かるか」を先に伝える。作業時間・公開計画・照合中の報告は制作メモへ。
- 「記事へ分離」「入口を整理」「画像は転載しない」などの制作説明を紹介文にしない。リンク先の具体的な見どころを書く。
- 不確実性は削らず、「この数字だけでは設定を判断できない」など読者への影響を明記する。
- 出典と重要な訂正は残す。軽微なレイアウト変更やファイル移動を本文の更新履歴に並べない。
- templates/*.json の editor_notes は制作側の指示。公開本文には出力しない。角括弧の仮文は公開前にすべて置き換える。
- 実戦写真は該当場面の直後に置き、alt・幅/高さ・説明文・撮影者/出典を用意。未掲載の同じ場面を大量に並べない。
- ATのTOTAL表示・回収枚数・差枚を混同しない。グラフの線から正確な収支を読み取ったことにしない。
- 既存の実戦画像は元の画素を保持し、EXIFのみ除去したもの。今後の追加画像は下記基準で整える。ユニメモ画面はCSSでグラフ部分を表示し、グラフの数値・線は改変しない。

## 今後追加する画像の基準

原本は別途保管し、公開用のコピーを作る。画像を拡大せず、縦横比を維持して縮小する。

| 用途 | 公開用の寸法 | 形式 | 1枚の容量目安 |
|---|---|---|---|
| 筐体・終了画面などの写真 | 長辺1200px以下 | JPEG | 150〜300KB |
| 数値・文字を含む縦長スクリーンショット | 横幅900px以下、縦は比率を維持 | JPEG、文字が崩れる場合はPNG | 200〜500KB |
| SNS共有画像 | 1200×630px | 既存のPNGを継続 | 500KB以下を目安 |

- 容量目安を満たすために証拠となる数値や文字を読めなくしない。必要なら上限の例外とし、掲載前に理由を確認する。
- JPEG品質は80〜85を出発点に調整し、書き出した画像をスマートフォン相当の表示幅で確認する。
- スクリーンショットの余白・広告・不要な操作部分は、説明に必要な内容を残してトリミングする。示唆画面、数値、グラフ、実戦の意味を変える加工はしない。
- EXIFなど不要なメタデータを除去し、個人情報の写り込みを確認する。原本の保存先を公開リポジトリに追加しない。
- HTMLには公開用ファイルの実寸のwidth/heightとaltを指定する。本文中の画像はloading="lazy"を使用し、最初に見える主画像は遅延させない。
- 既存画像は一括変換しない。差し替える場合は別の変更として、文字の判読性と意味の保持を確認する。

## 777リーグの日程一覧

- 機種別の本人実戦とは分け、league/777league/に非公式の観戦用ページを配置。
- data/league-4th.jsonに収録日、実戦状況、放送・配信日、確認元を記録。
- 「終了」は日付だけで判定せず、収録実施の裏付けURLと確認内容を残す。予定日を過ぎただけなら「終了確認待ち」。延期・中止も区別。
- 放送日が照合できない場合は「未確認」。未発表・未放送と推定しない。複数動画への分割や公開予定日を公式で確認した際は、動画ごとに日付・視聴リンクを追加できるようデータ形式を拡張する。
- 日付と状況は確認基準日現在の静的情報。自動更新ではない。基準日を進めるときに、終了・延期・中止を再照合する。
- 二次資料の会場法人・リーグに不整合があるものは会場を確認待ちにする。参照資料から公式確認済みと偽らない。
- python3 scripts/slot-tankyu/league_schedule.py → build.py → check.pyの順で生成・検査。公開は通常の承認とPR検査を経る。

## 新台カレンダーと業界ニュース

- 新台カレンダーの対象はパチスロのみ。パチンコは掲載しない。data/new-machines.jsonに全国導入予定、正式機種名、メーカー、種別、確認日、日程資料とメーカー公式のURLを記録。メーカーで導入日まで照合したものと、発売発表のみ・日程資料のみのものを区別する。
- data/industry-news.jsonは号の日付ごとに保存。公表・掲載日、出来事の日付、短い事実要約、編集者の考察、確認元の区分を別フィールドにする。
- ニュース原文や他社の写真・PDFを複製しない。短い要約と原文リンクを掲載。噂を確定情報に変えない。制度変更は施行・適用日まで照合し、検定通過を発売・導入決定と扱わない。
- 定期収集は直近7日、新台は今後8週間を中心とし、過去号はアーカイブとして残す。初回や前回情報がない場合は差分確認できないと報告する。
- 毎週月曜朝に収集結果をユーザーへ報告するタスクを設定。タスクは検索・非公開報告までとし、リポジトリや公開サイトへ自動書き込みをしない。承認された候補を安全検査とPR検査を経て反映する。
- 個人用の分析や更新候補は公開本文に含めない。読者には情報基準日、掲載範囲、出典、何を判断できるかを示す。
- 新規有料サービス、トラッカー、外部スクリプト、APIキーは追加しない。
- python3 scripts/slot-tankyu/news_calendar.py → build.py → check.pyで生成・検査する。日程表とニュースは静的情報であり、ページを開くだけで自動更新はしない。

- 決起集会は `rallies`、本編全体の公開開始は `battle_release_start` に記録。収録データの `broadcast_date` に本編開始日を一括転記しない。動画告知の確認日と収録情報の基準日は別に保持する。

- 読者向けの日付表示は月・日をゼロ埋めしない（例：2026年11月1日、1/1）。データ・HTMLのdatetime属性は標準のISO形式を保持する。「日時は日本時間」の注記は掲載しない。

## 主張の根拠と別工程の内容検証

新規記事・重要な事実の更新は [editorial/README.md](editorial/README.md) の手順を使用する。根拠表と内容検証記録を別々に残し、対象原稿の版を対応付ける。既存の生成・安全検査、ユーザー承認、PR公開手順を維持する。独立担当が未実施の場合は、独立検証済みと表示しない。

作業開始時は AGENTS.md と [決定記録](editorial/DECISIONS.md)、[作業記録](editorial/WORKLOG.md) を確認する。

## 任意の「シュウ３のコメント」

ページJSONの `author_comment` に、本人から提供された文章を段落ごとのプレーンテキスト配列で記録する。配列を省略・空にした記事にはコーナーも目次も出さない。値はHTMLとして扱わず、ビルド時にエスケープする。確認元の直前に本人の感想として表示し、確認元節がない場合は本文末尾に表示する。

編集は誤字・脱字・日本語のつながりの修正のみ。反復、口語、強い気持ち、率直な不満や期待を残す。感想をAIが追加せず、一般的な機種仕様・解析の説明にも書き換えない。意味が複数に取れて直せない場合だけ確認する。

コメントは任意。投稿前には有無を聞かず、未提供でも記事の投稿を止めない。公開後の報告に「コメントがあれば送ってください。後から追加できます。」と添える。既に受領した記事では再度求めない。コメント追加の公開は既存の承認・検証・PR手順を維持する。

## スロ番組ウォッチ

`templates/watch.json` をコピーして個別記事を作り、`pages/watch-listing.json` とトップのwatch節に追加する。共通メニューの「番組」から一覧へ移動できる。YouTubeへの通常リンクだけを使い、動画iframe・外部画像・外部スクリプト・トラッカーは追加しない。

- タイトル・チャンネルは公式ページまたはYouTube公式oEmbedと照合。oEmbedは編集時の確認だけに使用し、ブラウザーからAPIへ通信しない。公開日を確認できなければ省略し、紹介日と混同しない。
- 概要は2〜3文で番組の入口を紹介。勝敗、最終差枚、意外な展開、見せ場の発生や時間位置を出さない。動画タイトルに含まれる結末も紹介文で繰り返さない。必要なら結果を伏せたリンクラベルにする。
- 本文を直接視聴・取得できず本人の視聴メモを用いる場合は、概要の近くにその区分を明記する。動画本文の独立検証済みとはしない。メモ由来の仕様や確率を一般的な解析事実へ昇格させない。
- 本人コメントは既存の `author_comment` を使用。コメント未提供でも記事は止めず、空欄も出さない。提供済み文の熱量を保ち、表記と日本語のつながりのみ校正する。
- 新規記事の根拠表・別実行による独立検証・生成・安全・表示検査・公開承認は通常手順に従う。

777リーグ関連の視聴記事は、`data/league-4th.json` の該当 `rallies` に `watch_slug`（watch配下の記事ID）を追加し、`league_schedule.py` → `build.py` → `check.py` で再生成する。公式チャンネルリンクとサイト内の感想リンクを分け、収録実施・動画公開の確認日を導線追加だけで更新しない。記事側からリーグ日程表にも戻れるようにする。

「YouTubeで見る」の動画ボタンは `target="_blank" rel="noopener noreferrer"` を指定し、新しいタブで開く。新規記事でも `templates/watch.json` の指定を維持する。

## Web改善の共通生成（2026年10月16日）

- トップの横断新着は `data/latest.json`。`source` は掲載済みページJSON名、ニュースは実在する記事IDを `anchor` に指定する。`date_kind` は記事公開日／内容更新日／紹介日を明示し、`reason` に原稿・号などの日付根拠を残す。公開日不明は推定せず、動画公開日や実戦日で代用しない。重要な内容更新だけ登録し、CSS変更では日付を進めない。
- 最新4〜6件を降順表示。同日は登録順で時刻を推定しない。同内容の機種別と当日まとめには同じ `group` を使う（現在の登録は機種別のみ）。過去の重要ガイド更新はデータに残し、上位枠が空けば表示する。
- 日付別全件一覧は `type=daily` と日付別パスから自動生成。トップは最新3日分、`records/#dates` は全件。新しい日付別記事を追加したらトップと全件の両方に反映される。
- `data/presentation.json` の `as_of` は予定表示を整理する日付。収録や新台の情報確認日を上書きしない。未来の予定と過去の終了確認待ちを分けるだけで、収録実施・延期・中止・動画公開を推定しない。更新後はleague→news_calendar→build→checkの順に再生成する。公開HTMLは静的で、閲覧日には自動更新されない。
- ガイドの `quick_links` は実在する掲載項目だけ指定。タコスロは現在、ユニメモの読み方と記録を対象とし、未掲載の設定解析への入口を作らない。
- 実戦の `author_excerpt` は任意。`author_comment` に含まれる文を正確に抜粋し、否定・懸念・評価の範囲を保つ。ビルドは原文の連続一致を要求するが、意味の保持は編集でも確認する。全文は変更しない。
- 機種パスからガイドと実戦を自動関連付けする。関連番組は `machine_slug` を明示して同じ回遊欄に表示。記事が存在しないカテゴリーは出力しない。機種ガイドを既存の機種入口として使い、新しい機種ハブは作らない。
- 日付は表示テキストだけ年月日へ整形。URL・アンカー・datetime・ISOデータを保持。本人コメントは原文優先で自動整形しない。リーグ月別表は年・月の見出しと月/日（曜）で表し、既存の列幅・枠内スクロールを維持する。
- `python3 scripts/slot-tankyu/check_editorial.py` はR01〜R09の静的回帰確認。今回の基準コミットとの本文・数値・写真保持照合を含むため、次回以降に正当な記事追加がある場合は新しい対象範囲と根拠を確認して基準を更新する。ブラウザー表示の合格を意味しない。
- 共有画像だけを再生成する場合は `share_images.py --font /path/to/font.otf --page ページJSON名` を使用できる。公開用の外部フォント配信や依存追加は不要。
